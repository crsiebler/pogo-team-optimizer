## Codebase Patterns
- Ordered bring-6 pick-3 lineup enumeration lives in `application/lineups.py`; `OrderedLineup` canonicalizes the unordered back pair by sorted row index while preserving lead order from the input roster.
- Ordered lineup resource-path scoring lives in `application/lineups.py`; fixed paths are balanced lead 1/back 1, shield-spend lead 2/back 0, and shield-save lead 0/back 2, with lineup thresholds of `> 600` dominating and `< 400` overwhelming.
- Six-Pokemon roster objective scoring in `TeamOptimizer` should prioritize appended lineup-depth metrics before legacy full-roster coverage tie-breakers; keep score tuple indexes `0` through `12` compatible for existing metrics consumers.
- `TeamOptimizer` derives a meta-relative bulk floor from the loaded candidate pool mean and applies any below-floor bulk deficit in `_comparison_key()` before lineup objective fields; this is a penalty, not a legality filter.
- `TeamOptimizer` caches pure score results per optimizer instance: full team scores by sorted row-index identity and ordered lineup mean scores by `OrderedLineup`; comparison keys are not cached because safety and policy inputs vary per call.
- Optimizer multiprocessing should use `ProcessPoolExecutor` over deterministic restart batches with worker seeds derived from the base seed, cap worker counts via `MAX_OPTIMIZER_WORKERS`, and avoid parallelizing matchup cells or lineup resource-path calculations.
- Structured `recommended_lineups` assembly lives in `AnalyzeMetaUseCase`; rank by lineup score with row-index tie-breakers, source diagnostics from `application/lineups.py`, and keep CLI/exporters from computing lineup scores.
- Bench utility diagnostics live in `application/lineups.py` and are exposed as structured `recommended_team.bench_utility`; keep them diagnostic-only and do not feed them into optimizer ranking.
- Battle Frontier lineup point diagnostics are optional use-case result fields; compute usage rates and point-aware bench warnings from viable ordered lineups without rejecting individual pick-3 lineups.
- ABC/ABB/ABA lineup shape labels are heuristic diagnostics from `application/lineups.py`; expose them on `recommended_lineups` but never use them for lineup scoring, roster ranking, or tie-breaking.
- CSV lineup-aware exports keep the stable `section,key,value` schema and use `recommended_lineup`, `recommended_lineup_resource_path`, `bench_utility`, and `bench_utility_warning` sections.
- Excel lineup-aware exports use dedicated `Lineups`, `Lineup Resources`, `Bench Utility`, and `Bench Warnings` sheets instead of overloading legacy sheets.
- Human-readable text and Markdown reports should focus normal output on Recommended Bring-6 Roster, Team Analysis, Recommended Lineups, actionable warnings, and Potential Threats; do not reintroduce standalone Coverage, Safe Cores, or Resource / Shield Safety sections.
- Bench utility diagnostics should render in human-readable reports only when they contain actionable warnings; all-core/non-warning utility rows stay out of normal text and Markdown output.
- Normal `AnalyzeMetaUseCase` execution keeps `recommended_team.bench_utility` as an empty list unless actionable Battle Frontier warnings are needed; preserve the key for exporter compatibility instead of emitting all-core rows.
- CLI/report lineup count control is `--top-lineups` with a maximum of `10`; `AnalyzeMetaUseCase.execute(top_lineups=...)` limits `recommended_lineups`, and normal execution should not compute safe-core rankings.
- README CLI/performance docs should keep `--top-lineups`, `WORKERS`, `DIAGNOSTICS`, process-based restart batching, and simplified human-readable output semantics together so user-facing controls stay aligned with Makefile and CLI behavior.
- Register meta-specific auxiliary inputs in `data/metas.json` using typed ranking path mappings and `required_files`, then validate those paths in the CLI before constructing repositories.
- Keep meta config changes in `application/meta_config.py`; the CLI should only consume `MetaConfig` and enforce startup validation.
- Battle Frontier point data lives in `data/battle_frontier/` as `species,points` CSVs keyed by `parse_species()` names, and the repository should default missing species to `0`.
- Resolve switch rankings in the CLI as explicit `--switch-rankings-path` override, then per-meta `ranking_paths.switches`, then the legacy Great League default path.
- Meta-specific PvPoke ranking inputs live in `data/metas.json` as typed `ranking_paths` plus optional `full_meta_ranking_paths` keyed by `RankingCategory`; keep `switch_rankings_path` as a compatibility shim only.
- The CLI validates every configured category ranking path before constructing repositories; explicit `--switch-rankings-path` remains the highest-priority switch-only override.
- Battle Frontier legality belongs in `TeamOptimizer`; pass per-row point costs from the use case so `_random_team()` and swap-based local search both share the same legality gate.
- Battle Frontier output metrics belong in `recommended_team.metrics`; keep them optional and have human-readable exporters render a conditional legality section so non-`bfmaster` metas do not need placeholder fields.
- For real-data integration coverage, instantiate the concrete CSV repositories directly in tests so `bfmaster` assertions exercise the checked-in matrices, switch rankings, and Battle Frontier points files together.
- Ranking threat pool construction lives in `application/ranking_pools.py`; align ranking profiles to normalized matrix opponent labels, deduplicate by `parse_base_species()` like the optimizer, and use deterministic missing-score fallback weights/order.
- Ranking-aware weighted score structures live in `application/scoring.py`; preserve deterministic component order, neutral missing-component handling, and centralized `RosterScoreWeights` defaults before wiring them into optimizer ranking.
- PvPoke category score normalization lives in `application/scoring.py`; keep raw `RankingRow.score` values for diagnostics, store derived valid `normalized_score` values on a `0.0` to `1.0` scale, store invalid values as `None`, and use neutral `0.5` fallback for missing, invalid, or degenerate category lookups.
